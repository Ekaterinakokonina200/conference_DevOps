\# Правила внесения изменений



\## 1. Общие положения



Настоящий документ определяет правила работы команды над проектом Conference Management System.



Все изменения должны проходить через единый Git-процесс:



Issue → отдельная ветка → осмысленные коммиты → проверки → Pull Request → review → Approve → merge.



Прямое внесение изменений в ветку `main` запрещено.



\## 2. Создание задачи



Каждое функциональное изменение, исправление или изменение документации начинается с новой GitHub Issue.



Issue должна содержать:



\* понятное название;

\* описание задачи;

\* перечень необходимых изменений;

\* критерии приёмки;

\* назначенного исполнителя.



Если предыдущая Issue уже закрыта, повторно использовать её нельзя. Для новых изменений создаётся новая Issue.



\## 3. Подготовка к работе



Перед созданием новой ветки необходимо перейти в `main` и получить последние изменения:



```powershell

git switch main

git pull --ff-only origin main

```



Рабочая папка должна быть чистой:



```powershell

git status

```



Ожидаемый результат:



```text

nothing to commit, working tree clean

```



\## 4. Правила создания веток



Для каждой Issue создаётся отдельная ветка.



Разрешённые префиксы:



\* `feature/` — новая функциональность;

\* `fix/` — исправление ошибки;

\* `test/` — тесты;

\* `docs/` — документация;

\* `chore/` — служебные изменения;

\* `demo/` — учебная демонстрация Git-процесса.



Примеры:



```text

feature/payments

fix/participant-deletion

test/application-payment-rule

docs/technical-specification

docs/project-documentation

demo/conflict-source

demo/conflict-resolution

```



Ветка создаётся от актуального `main`:



```powershell

git switch -c docs/project-documentation

```



Название ветки должно кратко отражать выполняемую задачу.



\## 5. Правила создания коммитов



Один commit должен содержать одно логически завершённое изменение.



Коммиты не должны объединять несвязанные изменения.



Сообщение commit должно быть кратким и понятным.



Рекомендуемые префиксы:



\* `feat:` — новая функция;

\* `fix:` — исправление;

\* `test:` — тест;

\* `docs:` — документация;

\* `chore:` — служебное изменение;

\* `refactor:` — изменение структуры без изменения поведения.



Примеры:



```text

feat: add payment deletion endpoint

test: cover application confirmation payment rule

docs: add technical specification

docs: add HTTP API reference

chore: resolve contribution rules merge conflict

```



Перед commit необходимо проверить изменённые файлы:



```powershell

git status

git diff

```



Файлы добавляются явно:



```powershell

git add docs/api.md

```



Не рекомендуется без проверки выполнять:



```powershell

git add .

```



\## 6. Обязательные проверки



Перед созданием Pull Request необходимо выполнить:



```powershell

ruff check .

python -m pytest

git diff --check

```



Ожидаемые результаты:



\* Ruff сообщает `All checks passed!`;

\* все тесты pytest имеют статус `passed`;

\* `git diff --check` не выводит ошибок.



Состояние миграций проверяется командами:



```powershell

alembic current

alembic heads

```



Текущая и последняя доступная миграции должны совпадать.



\## 7. Отправка ветки



Новая ветка отправляется командой:



```powershell

git push -u origin <название-ветки>

```



Пример:



```powershell

git push -u origin docs/project-documentation

```



Последующие изменения отправляются командой:



```powershell

git push

```



\## 8. Pull Request



Pull Request создаётся из рабочей ветки в `main`.



PR должен содержать:



\* понятное название;

\* ссылку на Issue;

\* перечень выполненных изменений;

\* перечень добавленных или изменённых файлов;

\* результаты обязательных проверок.



Для автоматического закрытия Issue используется:



```text

Closes #<номер Issue>

```



Пример описания:



```markdown

Closes #25



\## Выполнено



\- добавлено описание API;

\- добавлены правила внесения изменений;

\- добавлена инструкция ручного тестирования.



\## Проверки



\- \[x] ruff check .

\- \[x] python -m pytest

\- \[x] git diff --check

```



\## 9. Review



Каждый Pull Request должен быть проверен другим участником команды.



Автор PR не должен одобрять собственные изменения.



Проверяющий должен:



1\. Открыть вкладку `Files changed`.

2\. Проверить изменённые файлы.

3\. Убедиться, что задача выполнена.

4\. Проверить отсутствие секретов.

5\. Проверить результаты Ruff и pytest.

6\. Нажать `Review changes`.

7\. Выбрать `Approve`.



Если обнаружена проблема, проверяющий выбирает `Request changes` и описывает необходимые исправления.



\## 10. Слияние изменений



Слияние выполняется только после:



\* успешных обязательных проверок;

\* review другого участника;

\* получения `Approve`;

\* устранения замечаний.



После этого используется:



```text

Merge pull request → Confirm merge

```



После слияния локальный `main` обновляется:



```powershell

git switch main

git pull --ff-only origin main

```



\## 11. Запрещённые действия



Запрещается:



\* выполнять прямые коммиты в `main`;

\* выполнять `git push --force` в `main`;

\* сливать PR без review;

\* сливать PR с непройденными проверками;

\* добавлять файл `.env`;

\* добавлять реальные пароли;

\* добавлять токены и секретные ключи;

\* добавлять виртуальное окружение `.venv`;

\* добавлять `\_\_pycache\_\_`;

\* добавлять локальные базы данных;

\* добавлять файлы журналов;

\* удалять тесты только для прохождения проверки;

\* отключать Ruff только для успешного PR;

\* использовать чужую закрытую Issue для новой задачи.



\## 12. Секреты и локальные файлы



Файл `.env` не должен отслеживаться Git.



Проверка:



```powershell

git ls-files .env

```



Команда не должна выводить ничего.



Проверка правила `.gitignore`:



```powershell

git check-ignore -v .env

```



Локальные файлы проверяются командой:



```powershell

git ls-files |

&#x20;   Select-String -Pattern '(^|/)\\.env$|\\.venv|\_\_pycache\_\_|\\.pyc$|\\.db$|\\.sqlite$'

```



Команда не должна находить локальные файлы.



\## 13. Порядок приёмки



Изменение считается принятым, если:



1\. Создана GitHub Issue.

2\. Создана отдельная ветка.

3\. Выполнены изменения.

4\. Созданы осмысленные коммиты.

5\. Успешно выполнен `ruff check .`.

6\. Успешно выполнен `python -m pytest`.

7\. Успешно выполнен `git diff --check`.

8\. Создан Pull Request.

9\. Выполнен review другим участником.

10\. Получен `Approve`.

11\. Изменение слито в `main`.

12\. Локальный `main` обновлён.



\## 14. Версионирование



Первая завершённая версия проекта отмечается аннотированным тегом:



```text

v0.1.0

```



Тег создаётся только после завершения всех изменений и финальных проверок:



```powershell

git tag -a v0.1.0 -m "Lab 1: first working version"

git push origin v0.1.0

```
