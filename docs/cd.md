# Непрерывная доставка и проверка работающего релиза (ЛР №6)

Главное правило: **успешная сборка не равна успешному релизу.** Образ,
прошедший CI, становится выпуском только после того, как его развернули в
предэксплуатационном окружении staging и там прошла проверка релиза.

## 1. Окружение staging

| Что | Значение |
|---|---|
| Сервер | ВМ `conference-app`, Ubuntu Server 24.04, host-only `192.168.56.10` (ЛР №2) |
| Адрес приложения | http://192.168.56.10:8080 (порт открыт только на host-only адресе) |
| Запуск | Docker Compose, проект `conference-staging`, файл `deploy/staging/compose.yaml` |
| Сервисы | `db` (PostgreSQL 17.5, том `conference_staging_pgdata`), `migrate` (разовая задача), `app` |
| Настройки | `/srv/conference-staging/staging.env` на сервере (владелец `deploy`, права 600), шаблон — `deploy/staging/staging.env.example` |
| Состояние | `/srv/conference-staging/state/`: `running`, `running_status`, `last_good`, `previous_good`, `releases.log` |
| Резервные копии | `/srv/conference-staging/backups/` — копия БД перед каждыми миграциями, хранятся последние 5 |

Окружение staging отделено от рабочих компьютеров участников и от
окружения ЛР №2: своя база данных в своём томе, свой порт, свои пароли.

## 2. Доступ pipeline к серверу

* На сервере создан отдельный системный пользователь **`deploy`**: без пароля
  и без входа по SSH (SSH разрешён только администраторам, ЛР №2), без `sudo`,
  в группе `docker`. Он владеет только каталогом `/srv/conference-staging`.
* От его имени работает **GitHub Actions self-hosted runner** (служба
  `actions.runner.*`) с меткой `staging`. Runner сам подключается к GitHub
  исходящим соединением, поэтому серверу не нужен ни белый IP, ни открытый
  входящий порт, а в GitHub не хранится ни SSH-ключ, ни пароль сервера.
* На этом runner выполняются **только** задания развертывания: `deploy` в
  `ci.yml` (после публикации) и ручной `deploy.yml`. Остальные задания CI —
  на машинах GitHub. Это проверяет `make rules-check`.
* Код Pull Request на сервер не попадает: `deploy` запускается только для
  `push` в `main` и тегов `v*`, `deploy.yml` — только вручную; правила окружения
  `staging` разрешают только `main` и `v*`; запуск workflow из форков требует
  одобрения владельца (Settings → Actions).
* Группа `docker` даёт права, близкие к root на этом сервере. Поэтому
  пользователь `deploy` используется только для развертывания, а сервер staging
  не содержит других данных.

## 3. Как проходит развертывание

```text
 CI (ЛР 5): проверки ─► build (образ, анализ) ─► publish (ghcr.io, тег sha-xxxxxxx / X.Y.Z)
                                                      │ только main и теги v*
                                                      ▼
 deploy-staging (self-hosted runner, пользователь deploy, очередь deploy-staging)
   deploy/staging/deploy.sh deploy <тег>
     1. тег sha-xxxxxxx или X.Y.Z; staging.env содержит все настройки   ─┐ ошибка: работающая
     2. docker pull образа из registry (на сервере образ не собирается) ─┘ версия не меняется
     3. db healthy, резервная копия БД, миграции из нового образа        ─┐ ошибка: выпуск
     4. замена app, ожидание healthcheck (до 90 с)                       │ НЕ ПРИНЯТ,
     5. tools/release_check.py: контейнеры, /health, /version,           │ возврат —
        веб-интерфейс, основной сценарий                                 ─┘ rollback
     → выпуск ПРИНЯТ: last_good = тег, previous_good = прежний last_good
```

Задание `deploy-staging` завершается ошибкой, если не прошёл любой шаг, —
запуск CI становится красным, выпуск не считается успешным. Итог (ПРИНЯТ /
НЕ ПРИНЯТ) печатается в журнале, в сводке запуска и в `releases.log`.

## 4. Проверка релиза (`tools/release_check.py`)

| Шаг | Что проверяется |
|---|---|
| 1. Контейнеры | `db` и `app` в состоянии running, healthcheck = healthy, перезапусков нет, `app` работает из развёрнутого образа |
| 2. Служебный адрес | `GET /health` → 200 `{"status": "ok"}` |
| 3. Версия | `GET /version` → `version` и `revision` совпадают с метками образа (`org.opencontainers.image.version`, `.revision`) |
| 4. Веб-интерфейс | `GET /` → 200, страница с формой регистрации |
| 5. Основной сценарий | участник → заявка (pending) → подтверждение без оплаты отклонено (409) → оплата → заявка подтверждена; данные проверки удаляются |

Те же проверки локально: `make up`, затем `make release-check`.

## 5. Ограничения развертывания

* **Когда:** автоматически — только после успешного `publish` для `push` в
  `main` (образ `sha-<7 символов>`) и тегов `vX.Y.Z` (образ `X.Y.Z`); вручную —
  workflow **Deploy staging** только из ветки `main`.
* **Окружение GitHub `staging`** (Settings → Environments): разрешены только
  ветка `main` и теги `v*`; в нём видна история развертываний.
* **Одно развертывание за раз:** `concurrency: deploy-staging` с
  `cancel-in-progress: false` (общая очередь автоматического и ручного
  развертывания; идущее развертывание не прерывается, ожидать может одно —
  самое новое), на сервере — блокировка `flock` в `deploy.sh`.

## 6. Ручное развертывание тега и возврат версии

Actions → **Deploy staging** → Run workflow (Branch: `main`):

| action | tag | Что происходит |
|---|---|---|
| `deploy` | `sha-1a2b3c4` или `0.6.0` | развернуть конкретный опубликованный образ (с полной проверкой релиза) |
| `rollback` | — | если работающий выпуск не принят — вернуть последнюю принятую версию (`last_good`); иначе — версию, принятую до текущей (`previous_good`) |
| `status` | — | что работает, какие версии приняты, последние выпуски |

Возврат выполняется тем же сценарием, что и выпуск, и тоже проходит проверку
релиза. Схема БД при возврате не откатывается: миграции проекта только
добавляют объекты и совместимы с предыдущей версией; если миграция ломает
совместимость, вернуть данные можно из копии в `backups/`.

## 7. Типовые отказы

| Отказ | Где останавливается | Состояние staging |
|---|---|---|
| неверный тег (`sha-0000000`, `v0.6.0`) | шаг 1 (формат) или 2 (`образ … не найден в registry`) | работающая версия не изменена |
| отсутствует настройка в `staging.env` | шаг 1 (`не задана переменная …`) | работающая версия не изменена |
| registry недоступен | шаг 2 (`registry недоступен`) | работающая версия не изменена |
| неуспешный healthcheck | шаг 4 (`app не прошёл healthcheck`, журнал app) | выпуск не принят → исправить / rollback |
| приложение запущено, но сценарий не работает | шаг 5 (`release-check: РЕЛИЗ НЕ ПРИНЯТ`) | выпуск не принят → rollback |
| второе развертывание во время первого | очередь `deploy-staging` / `flock` | ждёт или отклоняется |

## 8. Защита доставки

`make rules-check` проверяет: `deploy` в `ci.yml` зависит от `publish` и
ограничен `main` и тегами `v*`; задания развертывания работают только на
runner `staging`, в окружении `staging`, в очереди `deploy-staging` без
прерывания и только через `deploy/staging/deploy.sh`; `deploy.yml` запускается
только вручную; в `deploy/staging/compose.yaml` нет `build` и `latest`, образ
задан тегом из registry; `deploy.sh` получает образ через `docker pull`,
выполняет `release_check.py` и использует `flock`. Файлы доставки записаны в
`.github/CODEOWNERS`.
