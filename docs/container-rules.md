# Правила контейнерного окружения

Контейнерное окружение (`Dockerfile`, `.dockerignore`, `compose*.yaml`,
`docker/`, `.env.docker.example`, а также `requirements.txt`, из которого
собирается образ) меняется только через Pull Request, в описании которого
приведён успешный вывод `make container-check`:

```text
container-check: контейнерное окружение принято
```

Если проверка не прошла, изменение не принимается. Все перечисленные файлы
записаны в `.github/CODEOWNERS`, поэтому GitHub требует Approve их владельца.

## 1. Что запрещено (проверяется автоматически, шаг 1 `make container-check`)

| № | Запрет | Как проверяется |
|---|---|---|
| 1 | Образ без версии или с тегом `latest` | каждый `FROM` в Dockerfile и каждый `image:` в Compose должен иметь явный тег, не `latest` |
| 2 | Внешний образ без дайджеста | `FROM` и `image:` внешних образов — в виде `имя:тег@sha256:…` (`make pin-images`); обновление дайджеста — отдельный PR |
| 3 | Запуск от root | в Dockerfile последний `USER` не `root`/`0`; в Compose `user:` не `root`/`0`; на шаге 3 проверяется UID **каждого** процесса в контейнере `app` (только 10001) и главного процесса `db` |
| 4 | Секреты в образе | в Dockerfile нет `ENV`/`ARG` с паролями и ключами и копирования `.env`; `.dockerignore` — белый список и не разрешает `.env`; на шаге 5 сгенерированные для проверки пароли ищутся в истории слоёв и переменных образа, файлы `.env*` — в `/app` |
| 5 | Секреты в `compose.yaml` | значения переменных `*PASSWORD*`, `*SECRET*`, `*_TOKEN` — только через `${...}` из `.env.docker`; `.env.docker` закрыт в `.gitignore` |
| 6 | Отключение healthcheck | нет `HEALTHCHECK NONE`, нет `healthcheck: disable: true`; у сервисов без собственного образа healthcheck обязателен |
| 7 | Публикация лишних портов | порт разрешено публиковать только сервисам из списка `ALLOWED_PUBLISHED` (`app` → 8000, для доп. задания `nginx` → 8080) и только на `127.0.0.1`; порт БД не публикуется |
| 8 | Отсутствие ограничений ресурсов | у каждого сервиса `deploy.resources.limits`: `cpus`, `memory`, `pids` |
| 9 | Ослабление изоляции | запрещены `privileged: true`, `network_mode: host`; БД подключается только к внутренней (`internal: true`) сети, данные БД — только в именованном томе |
| 10 | Shell-форма запуска | `CMD`/`ENTRYPOINT` — только в форме exec, иначе приложение не получит SIGTERM |

## 2. Что проверяется в работе (шаги 2–9)

| Шаг | Проверка |
|---|---|
| 2 | образ собирается, `db` и `app` становятся healthy, `migrate` завершается с кодом 0 |
| 3 | пользователи процессов (см. запрет 3) |
| 4 | `/health` отвечает 200, `alembic current` — `(head)` |
| 5 | секреты не попали в образ (см. запрет 4), пользователь образа — 10001 |
| 6 | данные сохраняются после `docker compose down` + `up` и после обновления образа (новая версия, пересоздание контейнеров) |
| 7 | `docker compose stop`: код завершения 0, быстрее 15 с, в журнале `Finished server process` |
| 8 | резервная копия, восстановление в **новый** том, совпадение числа записей во всех таблицах, данные доступны через API |
| 9 | потребление памяти каждым контейнером — не более 80 % ограничения |

## 3. Порядок изменения контейнерного окружения

1. Issue → ветка от свежего `main`.
2. Изменение `Dockerfile` / `compose.yaml` / … .
3. `make verify` (если менялся код) и **`make container-check`**.
4. Если проверка не прошла — исправить и повторить; правила не ослаблять.
5. Pull Request с выводом `make container-check` и `make critical-changes`,
   Approve владельца изменённого файла, слияние.
