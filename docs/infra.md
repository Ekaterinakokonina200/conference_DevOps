# Управление конфигурацией и воспроизводимая инфраструктура (ЛР №7)

Главное правило: **инфраструктура приводится к требуемому состоянию кодом и
автоматически проверяется после применения.** Ручные настройки серверов из
ЛР №2 и ЛР №6 описаны в Ansible; вручную изменённый параметр возвращается
повторным запуском.

## 1. Средство и узлы

* **Ansible** (`requirements-infra.txt`: ansible 14.6.0, ansible-core 2.21.6) —
  без агентов на узлах, подключение по SSH, описание состояния в YAML и
  шаблонах Jinja2, повторный запуск ничего не меняет, если состояние уже
  нужное.
* **Управляющий узел** — ВМ `conference-app`: пользователь `infra` (без sudo,
  без Docker), ключ SSH учётной записи `ansible` на узлах, GitHub runner с
  меткой `infra`. Ansible ставится скриптом `infra/run.sh` в виртуальное
  окружение пользователя строго по `requirements-infra.txt`.

| Окружение | Узел | Адрес | ВМ | Приложение |
|---|---|---|---|---|
| staging | `conference-app` | 192.168.56.10 | conference-app (ЛР №2, №6), она же управляющий узел | разворачивает CD ЛР №6 (`deploy/staging/deploy.sh`), Ansible готовит сервер и `staging.env` |
| production | `conference-prod` | 192.168.56.11 | conference-db из ЛР №2, переустановленная «с чистого листа» | запускает Ansible: служба `conference-app` (Docker Compose), версия задана в коде |

## 2. Параметры: общие, окруженческие, узловые, секретные

| Уровень | Файл | Примеры |
|---|---|---|
| общие | `infra/group_vars/all/common.yml` | часовой пояс, пакеты, администраторы, `ansible`/`deploy`, host-only сеть, порт SSH, образы |
| окруженческие | `infra/inventories/<окр>/group_vars/all/env.yml` | способ запуска приложения, версия, каталог, порт, срок жизни токена, зеркала Docker |
| узловые | `infra/inventories/<окр>/host_vars/<узел>.yml` | адрес, имя узла, адрес публикации порта, доп. пакеты, службы-наследие ЛР №2 |
| секретные | `infra/inventories/<окр>/group_vars/all/vault.yml` (ansible-vault) | пароль БД, секрет JWT, хеши паролей администраторов |

Правила (проверяет `make infra-check`): имя параметра задаётся только на одном
уровне; у окружений одинаковый набор параметров; секреты — только `vault_*`
в зашифрованном `vault.yml`, в остальных файлах — ссылки `{{ vault_… }}`.
У каждого окружения свой пароль vault.

## 3. Что описано кодом

| Роль | Состояние |
|---|---|
| `base` | имя узла, часовой пояс, пакеты (общие + узловые), службы ЛР №2 остановлены |
| `users` | `ansible` (ключ, sudo без пароля), администраторы (ключи только из репозитория, sudo с паролем), `deploy` (группа docker, без пароля и sudo) |
| `ssh` | шаблон `00-conference-hardening.conf`: без root, без паролей, `AllowUsers`; другие файлы в `sshd_config.d` удаляются |
| `docker` | пакеты, шаблон `daemon.json` (ротация журналов, зеркало, live-restore), служба |
| `firewall` | ufw: входящие запрещены, разрешены SSH и порт приложения из host-only сети; правила не из кода удаляются |
| `app` | каталог (750, `deploy`), шаблон файла настроек с секретами (600); в production — шаблоны `compose.yaml` и службы `conference-app`, служба запущена |

Шаблоны: `sshd-hardening.conf.j2`, `sudoers-automation.j2`, `daemon.json.j2`,
`app.env.j2`, `compose.yaml.j2`, `conference-app.service.j2`.

Плейбуки: `bootstrap.yml` (подготовка чистой машины), `site.yml` (требуемое
состояние), `verify.yml` (проверка).

## 4. Процесс

```text
 PR ──► infra-check (yamllint, ansible-lint, синтаксис, требования) — обязательная проверка
  │ слияние в main (изменены infra/…)
  ▼
 infra-staging:    site.yml → повторный site.yml (changed=0) → verify.yml
  ▼ согласование в окружении infra-production
 infra-production: site.yml → повторный site.yml (changed=0) → verify.yml
```

Вручную на управляющем узле (`sudo -iu infra`): `bash infra/run.sh
check|apply|verify staging|production`. Подготовка чистой машины —
`bash infra/run.sh bootstrap production` от администратора (пароль
пользователя установщика), затем `apply`.

**Проверка после применения** (`verify.yml`): Docker работает, брандмауэр
включён и разрешает только SSH и приложение из host-only сети, SSH не пускает
root и вход по паролю, на внешних адресах слушают только порты 22 и 8080,
файл с секретами 600 и принадлежит `deploy`, приложение отвечает на `/health`
с управляющего узла, проверка релиза `tools/release_check.py` (ЛР №6) на узле
проходит.

## 5. Требования к инфраструктурному коду

1. **Нет лишних портов.** Снаружи — только SSH (22) и приложение (8080), только
   из host-only сети 192.168.56.0/24. Правила брандмауэра — только в роли
   `firewall`, ручные правила удаляются. Порт приложения публикуется только на
   host-only адресе узла; БД во внутренней сети Docker. Проверка: `make
   infra-check` (значения портов, правила вне роли, публикация порта) и
   `verify.yml` (слушающие порты и правила ufw на узле).
2. **Минимальные права.** Sudo без пароля — только у `ansible` (вход только по
   ключу управляющего узла). `deploy` — без пароля, sudo и SSH, только группа
   docker. Администраторы — sudo с паролем. Файл с секретами — 600, каталог
   приложения — 750. Режимы 777/666 и запись для всех запрещены. Pipeline
   работает от `infra` без sudo. Проверка: `make infra-check`, `verify.yml`.
3. **Нет необъяснимых shell-команд.** Состояние описывается модулями Ansible.
   Модуль `shell` запрещён; у `command`/`raw`/`script` обязательны комментарий
   `# Обоснование: …` и `changed_when`. Проверка: `make infra-check`.
4. **Повторяемость результата.** Повторный запуск без ручных изменений даёт
   `changed=0` — это проверяется при каждом применении (`run.sh apply`, шаг 2).
   Нет `state: latest`; обновление списка пакетов — с `cache_valid_time`;
   версии инструментов закреплены (`==`), образы — по дайджесту или тегу
   выпуска; пароли администраторов задаются только при создании.
5. **Секреты не хранятся в открытом виде.** `vault.yml` каждого окружения
   зашифрован (свой пароль), пароли vault — в секретах окружений GitHub и в
   файлах `~/.config/conference-infra/vault-<окр>` (600) на управляющем узле.
   В репозитории нет закрытых ключей. Проверка: `make infra-check`,
   `make secrets-scan` (ЛР №5).
6. **Обязательное согласование.** Роли, шаблоны, параметры, секреты, ключи и
   pipeline записаны в `.github/CODEOWNERS`; `infra-check` — обязательная
   проверка защиты `main`; применение к production — после согласования в
   окружении GitHub `infra-production`.
