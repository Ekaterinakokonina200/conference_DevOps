# Правила качества и проверочный контур

Любое изменение кода, тестов, миграций и настроек попадает в `main` только
после успешного выполнения `make verify` на компьютере автора и проверки
Pull Request другим участником.

## 1. Что запрещено

1. **Пропускать тесты.** Нельзя использовать `pytest.mark.skip`,
   `pytest.mark.skipif`, `pytest.mark.xfail`, `pytest.skip()`,
   `pytest.xfail()`, `pytest.importorskip()`, а также исключать тесты через
   `--deselect`, `--ignore`, `-k` в настройках. Падающий тест исправляют,
   а не отключают. Контроль: `make rules-check` (поиск в коде) и
   `tests/conftest.py` (прогон с пропущенным тестом завершается ошибкой).
2. **Снижать пороги.** Порог покрытия `fail_under` в `pyproject.toml` не может
   быть ниже значения `MIN_COVERAGE` в `tools/check_rules.py`. Порог можно
   только повышать.
3. **Добавлять исключения анализаторов без обоснования.**
   - Комментарии `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`
     разрешены только вместе с комментарием `# Обоснование: …` на той же
     или предыдущей строке.
   - Каждое правило в `ignore` / `per-file-ignores` (ruff) и `skips` (bandit)
     в `pyproject.toml` должно быть записано в журнал исключений ниже.
4. **Убирать шаги из `make verify`.** Список обязательных шагов зафиксирован
   в `tools/check_rules.py` (`REQUIRED_VERIFY_STEPS`).
5. **Ставить зависимости без фиксированной версии.** Все строки в
   `requirements.txt` и `requirements-dev.txt` — только с `==`.
6. **Сливать Pull Request с красным `make verify`** или без Approve другого
   участника.

Изменение самих правил (этого файла, `tools/check_rules.py`, порогов в
`pyproject.toml`) — отдельный Pull Request с объяснением в описании и
Approve двух других участников.

## 2. Критические файлы приёмки

Критические файлы приёмки определяют, как проверяется изменение:
`Makefile`, `pyproject.toml`, `requirements*.txt`, служебные скрипты
`tools/`, `tests/conftest.py`, `tests/integration/conftest.py`,
`tests/migrations/`, миграции `alembic/`, этот файл, каталог `.github/`,
файлы развёртывания `deploy/` и `scripts/`. Полный список с владельцами —
`.github/CODEOWNERS`.

Изменения этих файлов видны в Pull Request и проверяются отдельно:

1. `.github/CODEOWNERS` — GitHub сам добавляет владельцев файла в
   проверяющие PR и помечает такие файлы во вкладке Files changed.
2. Защита ветки `main` (Settings → Branches): слияние только через PR,
   не меньше 1 Approve, **Require review from Code Owners** — PR, меняющий
   критический файл, нельзя слить без Approve его владельца. У каждого файла
   два владельца, поэтому автор не проверяет себя сам.
3. `make critical-changes` выводит изменённые критические файлы; вывод и
   объяснение «зачем изменён» обязательны в разделе «Критические файлы
   приёмки» шаблона PR.
