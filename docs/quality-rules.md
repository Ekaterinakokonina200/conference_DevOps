# Правила качества и проверочный контур

Любое изменение кода, тестов, миграций и настроек попадает в `main` только
после успешного выполнения `make verify` на компьютере автора и проверки
Pull Request другим участником.

## 1. Что запрещено

1. **Пропускать тесты.** Нельзя использовать `pytest.mark.skip`,
   `pytest.mark.skipif`, `pytest.mark.xfail`, `pytest.skip()`,
   `pytest.xfail()`, `pytest.importorskip()`, а также исключать тесты через
   `--deselect`, `--ignore`, `-k` в настройках. Падающий тест исправляют,
   а не отключают. Контроль: `make rules-check` (поиск в коде) и
   `tests/conftest.py` (прогон с пропущенным тестом завершается ошибкой).
2. **Снижать пороги.** Порог покрытия `fail_under` в `pyproject.toml` не может
   быть ниже значения `MIN_COVERAGE` в `tools/check_rules.py`. Порог можно
   только повышать.
3. **Добавлять исключения анализаторов без обоснования.**
   - Комментарии `# noqa`, `# nosec`, `# type: ignore`, `# pragma: no cover`
     разрешены только вместе с комментарием `# Обоснование: …` на той же
     или предыдущей строке.
   - Каждое правило в `ignore` / `per-file-ignores` (ruff) и `skips` (bandit)
     в `pyproject.toml` должно быть записано в журнал исключений ниже.
4. **Убирать шаги из `make verify`.** Список обязательных шагов зафиксирован
   в `tools/check_rules.py` (`REQUIRED_VERIFY_STEPS`).
5. **Ставить зависимости без фиксированной версии.** Все строки в
   `requirements.txt` и `requirements-dev.txt` — только с `==`.
6. **Сливать Pull Request с красным `make verify`** или без Approve другого
   участника.

Изменение самих правил (этого файла, `tools/check_rules.py`, порогов в
`pyproject.toml`) — отдельный Pull Request с объяснением в описании и
Approve двух других участников.

## 2. Критические файлы приёмки

Критические файлы приёмки определяют, как проверяется изменение:
`Makefile`, `pyproject.toml`, `requirements*.txt`, служебные скрипты
`tools/`, `tests/conftest.py`, `tests/integration/conftest.py`,
`tests/migrations/`, миграции `alembic/`, этот файл, каталог `.github/`,
файлы развёртывания `deploy/` и `scripts/`. Полный список с владельцами —
`.github/CODEOWNERS`.

Изменения этих файлов видны в Pull Request и проверяются отдельно:

1. `.github/CODEOWNERS` — GitHub сам добавляет владельцев файла в
   проверяющие PR и помечает такие файлы во вкладке Files changed.
2. Защита ветки `main` (Settings → Branches): слияние только через PR,
   не меньше 1 Approve, **Require review from Code Owners** — PR, меняющий
   критический файл, нельзя слить без Approve его владельца. У каждого файла
   два владельца, поэтому автор не проверяет себя сам.
3. `make critical-changes` выводит изменённые критические файлы; вывод и
   объяснение «зачем изменён» обязательны в разделе «Критические файлы
   приёмки» шаблона PR.

## 4. Анализ безопасности (SAST) и уровни угроз

`make sast` запускает bandit для каталога `app/` (`tools/sast_report.py`) и
выводит в терминал полный отчёт: сколько файлов и строк проверено, таблицу
замечаний по **важности** (severity — насколько опасна уязвимость) и
**уверенности** (confidence — насколько анализатор уверен, что это не ложное
срабатывание), каждое замечание с файлом, строкой и правилом, а также
замечания, подавленные исключениями `# nosec`, с их уровнями и обоснованием.
Тот же отчёт сохраняется в `reports/bandit.txt`, отчёты bandit — в
`reports/bandit.html` и `reports/bandit.json`; `make sast-report` открывает
HTML-отчёт в браузере.

| Важность | Примеры | Реакция |
|---|---|---|
| высокая (HIGH) | `subprocess` с `shell=True`, отключённая проверка сертификата TLS (`verify=False`), MD5/SHA1 для защиты данных | проверка останавливается, код исправляется |
| средняя (MEDIUM) | `eval`, `pickle`, привязка к `0.0.0.0` в коде, SQL-запрос, склеенный из строк | проверка останавливается, код исправляется |
| низкая (LOW) | пароль-похожая строка в коде, `assert` для проверок, `try/except/pass` | проверка останавливается: исправить код или оформить обоснованное исключение |

Порог не понижается: `make sast` завершается ошибкой при замечании **любой**
важности и уверенности, а также при метке `# nosec` без обоснования в
комментарии над строкой. Исключение допускается только для конкретного
правила на одной строке (`# nosec B106`), с обоснованием и записью в журнал
исключений (раздел 3).

## 5. Непрерывная интеграция (ЛР №5)

Pipeline — `.github/workflows/ci.yml`, описание — `docs/ci.md`.

1. **CI обязателен.** PR сливается в `main` только при зелёных обязательных
   проверках CI (`style`, `rules`, `security`, `tests`, `migrations`,
   `backup`, `container`, `build`) — это задано в защите ветки `main`.
2. **CI выполняет те же команды, что и локально** (`make …`). Добавлять в CI
   проверку, которой нет в `Makefile`, или проверять в CI иначе — запрещено.
3. **Нельзя ослаблять pipeline**: удалять задания и команды, добавлять
   `continue-on-error`, `if: false`, `|| true`, публиковать образ без всех
   проверок. Контроль: `make rules-check` (`REQUIRED_CI_JOBS`, `PUBLISH_JOB`).
4. **Нельзя удалять тесты.** `make rules-check` считает тестовые функции:
   их не меньше `MIN_TEST_FUNCTIONS`. Уменьшить минимум можно только PR с
   изменением `tools/check_rules.py` (CODEOWNERS) и записью в журнал (раздел 3).
5. **Пароли и токены — только в защищённых переменных** (`secrets`),
   действия GitHub закреплены по commit SHA.
6. **Безопасность.** Секрет в истории Git, а также уязвимость CRITICAL или
   HIGH с доступным исправлением в зависимостях или образе останавливают CI.
   Исключение — строка в `.trivyignore` / `.gitleaksignore` с комментарием
   `# Обоснование: …` над ней и записью в журнал (раздел 3).
7. **Образ публикуется только из `main` и тегов `v*`**, только после всех
   проверок, с тегом commit SHA.
