# Непрерывная интеграция (ЛР №5)

CI — независимый и обязательный барьер перед созданием и публикацией образа.
Система — **GitHub Actions**, файл pipeline — `.github/workflows/ci.yml`,
реестр образов — **GitHub Container Registry** (`ghcr.io`).

## 1. Когда запускается

| Событие | Что происходит |
|---|---|
| `push` в любую ветку | все проверки и сборка образа (без публикации) |
| `pull_request` в `main` | все проверки; результаты видны в PR, слияние блокируется, пока они не зелёные |
| `push` в `main` (слияние PR) | все проверки, сборка, **публикация** образа |
| `push` тега `v*` | то же, что для `main`, плюс тег образа с номером версии |
| `workflow_dispatch` | ручной запуск (Actions → CI → Run workflow) |

## 2. Задания pipeline

В CI выполняются **те же команды make**, что и локально. Ни одна проверка не
описана в CI «по-своему».

| Задание | Команды | Что проверяет | Пункт задания |
|---|---|---|---|
| `style` | `make format-check`, `make lint` | единый стиль, линтер ruff | 5 |
| `rules` | `make rules-check`, `make critical-changes` | запреты ослабления проверок, список критических файлов PR | 13–15 |
| `security` | `make sast`, `make secrets-scan`, `make deps-scan` | bandit, поиск секретов gitleaks, уязвимости зависимостей trivy | 5, 12 |
| `tests` | `make test`, `make mutation` | 143 unit- и интеграционных теста на отдельной БД, покрытие ≥ 90 %, мутации | 5, 6 |
| `migrations` | `make migrations-check` | миграции на чистой и заполненной БД | 5, 6 |
| `backup` | `make backup-check` | копия → порча → восстановление | 5, 6 |
| `container` | `make container-check` | 9 шагов проверки контейнерного окружения (ЛР №4) | 5 |
| `build` | сборка образа, `make image-scan` | образ с тегом commit SHA, анализ уязвимостей образа trivy | 5, 9, 12 |
| `publish` | `docker push` в `ghcr.io` | публикация **проверенного** образа | 5, 10 |

```text
 style ─────┐
 rules ─────┤
 security ──┤
 tests ─────┼──► build ──► publish (только main и теги v*)
 migrations ┤
 backup ────┤
 container ─┘
```

`build` начинается только после успеха всех семи заданий проверки (`needs`),
`publish` — только после `build` и всех проверок. Если упало любое задание,
`build` и `publish` получают статус **skipped**, образ не собирается и не
публикуется.

## 3. Тестовая база данных

Задания `tests`, `migrations`, `backup` поднимают собственный контейнер-сервис
PostgreSQL — тот же образ `postgres:17.5-bookworm@sha256:…`, что в
`compose.yaml`. База — `conference_test` (имя оканчивается на `_test`,
иначе тесты не запускаются). Каждое задание получает новую пустую БД,
рабочие данные недоступны. Адрес передаётся переменной `TEST_DATABASE_URL`,
пароль — из защищённой переменной `CI_DB_PASSWORD`.

Для `make backup-check` в задании ставится клиент PostgreSQL 17: `pg_dump`
должен быть той же версии, что сервер.

## 4. Защищённые переменные

| Переменная | Где задана | Зачем |
|---|---|---|
| `CI_DB_PASSWORD` | Settings → Secrets and variables → Actions → Repository secrets | пароль тестовой БД в CI |
| `GITHUB_TOKEN` | создаётся GitHub для каждого запуска | вход в `ghcr.io` в задании `publish` (права `packages: write` только у него) |

Значения секретов GitHub скрывает в журналах (`***`). В `ci.yml` пароли
только в виде `${{ secrets.… }}` — это проверяет `make rules-check`.
Пароли, которые нужны `make container-check`, генерируются заново при каждом
запуске и нигде не хранятся.

## 5. Кэширование

| Что | Чем | Ключ |
|---|---|---|
| пакеты pip | `actions/setup-python` (`cache: pip`) | хеш `requirements*.txt` |
| слои Docker при сборке образа | `docker/build-push-action` (`type=gha`) | содержимое слоёв |
| база уязвимостей trivy | `actions/cache` (`.cache/trivy`) | дата (обновляется раз в день) |

## 6. Отчёты

Отчёты сохраняются как артефакты запуска (Actions → запуск → Artifacts), в
том числе при ошибке:

| Артефакт | Содержимое |
|---|---|
| `test-reports` | `junit.xml`, `coverage.xml`, HTML-отчёт покрытия, вывод мутационной проверки |
| `migrations-report` | `migrations-junit.xml` |
| `backup-report` | вывод `make backup-check` |
| `security-reports` | bandit (txt, html, json), gitleaks (txt, json), trivy по зависимостям |
| `container-check-report` | вывод `make container-check` |
| `image-scan-report` | trivy по образу (txt, json) |
| `image` | проверенный образ (хранится 1 день, передаётся в `publish`) |

## 7. Образ и его теги

Образ: `ghcr.io/ekaterinakokonina200/conference-app`.

| Тег | Пример | Когда |
|---|---|---|
| полный commit SHA | `:2b0b4f8c…` | каждая публикация |
| `sha-` + 7 символов SHA | `:sha-2b0b4f8` | каждая публикация |
| версия | `:0.5.0` | push тега `v0.5.0` |

Тега `latest` нет: по тегу SHA всегда понятно, из какого коммита собран образ.
В образ записывается метка `org.opencontainers.image.revision` с тем же SHA.
Публикуется ровно тот образ, который прошёл анализ trivy в задании `build`
(передаётся артефактом, а не собирается заново).

## 8. Проверки безопасности

| Команда | Инструмент | Что ищет | Когда останавливает |
|---|---|---|---|
| `make sast` | bandit | небезопасный код | замечание любой важности |
| `make secrets-scan` | gitleaks | пароли, токены, ключи во всей истории Git | найден хотя бы один секрет |
| `make deps-scan` | trivy | уязвимости пакетов `requirements.txt` | CRITICAL или HIGH, для которой есть исправление |
| `make image-scan` | trivy | уязвимости пакетов ОС и Python в образе | CRITICAL или HIGH, для которой есть исправление |

Gitleaks и trivy запускаются из образов, закреплённых по дайджесту в
`docker/security-tools.yaml`, поэтому локально и в CI работают одни и те же
версии. Исключения — только в `.trivyignore` / `.gitleaksignore` с
комментарием `# Обоснование: …` над строкой (проверяет `make rules-check`).

Если секрет попал в коммит: удалить его из кода, **сменить** пароль или токен
(он уже считается раскрытым) и не сливать ветку; ветку с секретом удалить.

## 9. Защита pipeline и критических файлов

1. **CODEOWNERS.** `.github/` (в том числе `workflows/ci.yml`), `tests/`,
   `Makefile`, `pyproject.toml`, `tools/`, `docker/`, `.trivyignore` записаны
   в `.github/CODEOWNERS`. PR, меняющий их, нельзя слить без Approve
   владельца.
2. **Защита ветки `main`.** Слияние только через PR, обязательные проверки
   CI (`style`, `rules`, `security`, `tests`, `migrations`, `backup`,
   `container`, `build`), ветка должна быть актуальной, Approve владельцев
   кода, правила действуют и для администраторов. Список обязательных проверок
   хранится в настройках GitHub, а не в репозитории, поэтому PR не может его
   изменить: если из `ci.yml` удалить задание, его проверка не придёт, и PR
   останется заблокированным.
3. **`make rules-check`** (задание `rules`) отклоняет:
   * удаление тестов — тестовых функций меньше `MIN_TEST_FUNCTIONS`;
   * пропуск тестов, снижение порога покрытия, исключения без обоснования;
   * удаление задания или команды из `ci.yml`, `continue-on-error`,
     `if: false`, подавление ошибки (`|| true`);
   * публикацию без всех проверок (`publish.needs`), запуск публикации при
     ошибке (`always()`);
   * действия GitHub без закрепления по commit SHA, пароли в открытом виде.

## 10. Почему локальные и серверные проверки совпадают

* **Одни команды.** CI вызывает `make …`, а не свои скрипты: если
  `make verify` и `make container-check` прошли у разработчика, они пройдут
  и в CI, и наоборот — ошибку CI можно воспроизвести у себя одной командой.
* **Одни версии.** Зависимости зафиксированы через `==`, базовые образы,
  PostgreSQL и инструменты безопасности — по дайджесту.
* **CI — независимый арбитр.** Локальную проверку можно забыть, пропустить
  или запустить на изменённых файлах; CI запускается всегда, на чистой
  машине, с чистой БД, и его результат нельзя подделать. Но если бы CI
  проверял не то же, что локальный контур, разработчик узнавал бы об ошибках
  только после push, а «зелёный» локальный результат ничего бы не значил.

Все проверки CI локально: `make ci-local` (нужен Docker).
