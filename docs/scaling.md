# Nginx, масштабирование и отказоустойчивость (дополнительное задание ЛР №4)

Файлы: `compose.scale.yaml` (накладывается поверх `compose.yaml`),
`docker/nginx/default.conf`, `tools/scale_check.py`.

```text
 браузер ──► 127.0.0.1:8080 ──► nginx (UID 101) ──┬──► app, экземпляр 1 ──┐
                                                   └──► app, экземпляр 2 ──┴──► db
            порт 8000 приложения наружу НЕ опубликован
```

| Требование | Как выполнено |
|---|---|
| Nginx отдельным контейнером | сервис `nginx`, образ `nginxinc/nginx-unprivileged` (работает не от root, порт 8080) |
| Запрет прямого доступа к приложению | в `compose.scale.yaml` у `app` порт убран (`ports: !reset []`); наружу опубликован только порт Nginx на 127.0.0.1 |
| Не менее двух экземпляров | `deploy.replicas: 2` у сервиса `app` |
| Распределение запросов | `upstream conference_app { server app:8000; }` — имя `app` разрешается во все экземпляры, запросы идут по очереди (round robin) |
| Идентификатор экземпляра | `GET /version` возвращает `instance` (имя контейнера), Nginx добавляет заголовок `X-Upstream` |
| Остановка экземпляра | `make scale-check` останавливает один экземпляр и проверяет, что все запросы успешны |
| Исключение неработающего узла | `max_fails=2 fail_timeout=10s` — после двух ошибок экземпляр исключается на 10 с |
| Повтор запроса | `proxy_next_upstream error timeout http_502 http_503 http_504` — безопасные запросы повторяются на другом экземпляре (POST не повторяется) |
| Ограничение частоты | `limit_req` — 20 запросов/с с адреса, всплеск до 40, сверх — 429 |

## Команды

```bash
make up-scale      # db, migrate, 2 экземпляра app, nginx
make scale-check   # проверка: прямой доступ закрыт, балансировка, отказ, 429
make down-scale
```

## Что мешает горизонтальному масштабированию приложения

| Элемент | Почему мешает | Как решено или что нужно |
|---|---|---|
| Секрет JWT | токен, выданный одним экземпляром, проверяется другим; при разных `JWT_SECRET_KEY` пользователь «выходил» бы при каждом переключении | общий секрет из `.env.docker` для всех экземпляров |
| Миграции БД | если запускать `alembic upgrade` при старте каждого экземпляра, два экземпляра одновременно меняют схему | миграции — отдельный разовый сервис `migrate`, экземпляры стартуют после него |
| Одна база данных | все экземпляры пишут в один PostgreSQL: он остаётся единой точкой отказа и узким местом | масштабируются только экземпляры приложения; для БД нужны реплики/резервирование (вне рамок работы) |
| Пул соединений | у каждого экземпляра свой пул SQLAlchemy (до 15 соединений); при N экземплярах до 15·N соединений, лимит PostgreSQL — 100 | число экземпляров ограничено; при росте нужен пул соединений (PgBouncer) |
| Проверка уникальности при создании участника | «проверить, затем вставить» при двух экземплярах может пропустить дубликат | защищает уникальный индекс в БД (`IntegrityError` → 409) |
| Healthcheck `/health` не проверяет БД | экземпляр с потерянным соединением к БД считается здоровым и получает запросы | `pool_pre_ping=True` восстанавливает соединения; для строгой проверки нужен отдельный `/ready` с запросом к БД |
| Журналы | у каждого экземпляра свой журнал контейнера | для анализа нужен общий сбор журналов (`docker compose logs` объединяет их локально) |
| Статические файлы | веб-интерфейс отдаёт каждый экземпляр | можно отдавать из Nginx и снизить нагрузку на приложение |
| Отзыв токенов | JWT не хранится на сервере, поэтому «выйти на всех экземплярах» нельзя до истечения срока | при необходимости — общий список отозванных токенов (Redis) |

Состояния в памяти процесса (сессий, кэшей, счётчиков) в приложении нет,
поэтому запросы одного пользователя можно обрабатывать на любом экземпляре —
привязка к экземпляру (sticky sessions) не нужна.
