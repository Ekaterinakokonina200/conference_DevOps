# Ограничения ресурсов контейнеров

Ограничения задаются в `compose.yaml` (`deploy.resources.limits`) и
проверяются `make container-check`: на шаге 1 — что они заданы у каждого
сервиса, на шаге 9 — что фактическое потребление ниже 80 % лимита.

| Сервис | CPU | Память (лимит / резерв) | Процессы | Обоснование |
|---|---|---|---|---|
| `db` | 1.0 | 512 МБ / 128 МБ | 200 | PostgreSQL по умолчанию использует `shared_buffers` = 128 МБ и по нескольку МБ на каждое соединение; 512 МБ — запас для 30–40 соединений и сортировок отчёта. Число процессов: по одному на соединение плюс служебные (~10) |
| `app` | 1.0 | 384 МБ / 64 МБ | 100 | один процесс uvicorn с FastAPI и SQLAlchemy занимает 60–100 МБ; лимит в 4 раза выше покоя оставляет запас на всплески, но не даёт утечке памяти занять весь ноутбук. В контейнере один процесс uvicorn (плюс кратковременные процессы healthcheck) |
| `migrate` | 0.5 | 256 МБ | 50 | разовая задача Alembic работает несколько секунд и занимает 50–80 МБ |

Почему ограничения нужны: без них один контейнер (например, приложение с
утечкой памяти или зациклившийся запрос) может занять всю память и процессор
компьютера, и вместе с ним перестанут работать БД и Docker Desktop. При
превышении лимита памяти ядро завершает только этот контейнер
(OOM, код 137), а `restart: unless-stopped` поднимает его снова.

|---|---|---|---|---|
