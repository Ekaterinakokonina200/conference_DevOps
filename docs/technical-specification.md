## 2. Назначение системы

Система предназначена для автоматизации основных процессов
подготовки и проведения научной конференции.

Система обеспечивает:

- регистрацию учётных записей;
- аутентификацию пользователей;
- регистрацию участников;
- создание заявок;
- создание приглашений;
- регистрацию организационных взносов;
- учёт тезисов;
- учёт потребности в гостинице;
- формирование сводного отчёта;
- работу через HTTP API;
- работу через Web-интерфейс.

## 3. Цели разработки

Целями разработки являются:

- централизованное хранение данных;
- сокращение ручной обработки информации;
- контроль статусов заявок;
- контроль оплаты организационных взносов;
- выполнение бизнес-правил;
- предоставление базовой аутентификации;
- автоматизация сводной отчётности;
- предоставление HTTP API;
- предоставление Web-интерфейса;
- демонстрация командного Git-процесса.

## 4. Категории пользователей

Предполагаемыми пользователями являются:

- организатор конференции;
- секретарь конференции;
- оператор, работающий с данными;
- зарегистрированный пользователь системы.

Зарегистрированный пользователь может выполнить вход, получить JWT
и запросить сведения о собственной учётной записи.

Ролевая модель и разграничение прав между организатором,
секретарём и оператором в текущей версии не реализованы.

Маршрут `GET /auth/me` защищён JWT. Остальные маршруты управления
конференцией в текущей версии остаются общедоступными.

## 5. Основные сценарии использования

Пользователь может:

1. Зарегистрировать учётную запись.
2. Выполнить вход.
3. Получить JWT.
4. Получить сведения о текущем пользователе.
5. Выйти из учётной записи.
6. Зарегистрировать участника.
7. Просмотреть список участников.
8. Изменить данные участника.
9. Удалить участника.
10. Создать заявку.
11. Изменить статус заявки.
12. Создать приглашение.
13. Изменить статус приглашения.
14. Зарегистрировать оплату.
15. Изменить статус оплаты.
16. Добавить тезис.
17. Изменить статус тезиса.
18. Создать запрос на гостиницу.
19. Получить сводный отчёт.
20. Проверить работоспособность приложения.

## 6. Функциональные требования

### 6.1. Аутентификация

Система должна обеспечивать:

- регистрацию пользователя;
- проверку уникальности username;
- хеширование пароля;
- вход по username и password;
- выдачу JWT;
- ограничение срока действия JWT;
- проверку подписи JWT;
- получение текущего пользователя;
- отказ при отсутствии или недействительности JWT.

Регистрация выполняется через:

```http
POST /auth/register
```

Вход выполняется через:

```http
POST /auth/login
```

Получение текущего пользователя выполняется через:

```http
GET /auth/me
```

### 6.2. Управление участниками

Система должна обеспечивать:

- создание Participant;
- получение списка Participant;
- получение Participant по идентификатору;
- изменение Participant;
- удаление Participant;
- проверку уникальности email.

### 6.3. Управление заявками

Система должна обеспечивать:

- создание Application;
- получение списка Application;
- получение Application по идентификатору;
- изменение статуса Application;
- удаление Application.

### 6.4. Управление приглашениями

Система должна обеспечивать:

- создание Invitation;
- получение списка Invitation;
- получение Invitation по идентификатору;
- изменение статуса Invitation;
- удаление Invitation.

### 6.5. Управление оплатами

Система должна обеспечивать:

- создание Payment;
- получение списка Payment;
- получение Payment по идентификатору;
- изменение статуса Payment;
- удаление Payment.

### 6.6. Управление тезисами

Система должна обеспечивать:

- создание Thesis;
- получение списка Thesis;
- получение Thesis по идентификатору;
- изменение статуса Thesis;
- удаление Thesis.

### 6.7. Управление гостиницей

Система должна обеспечивать:

- создание HotelRequest;
- получение списка HotelRequest;
- получение HotelRequest по идентификатору;
- изменение HotelRequest;
- удаление HotelRequest.

### 6.8. Формирование отчёта

Система должна формировать отчёт по адресу:

```http
GET /reports/summary
```

Отчёт должен содержать:

- количество участников;
- количество подтверждённых заявок;
- количество оплат со статусом `paid`;
- количество зарегистрированных тезисов;
- количество запросов на гостиницу.

Report не является отдельной таблицей. Он формируется динамически
на основании существующих данных.

### 6.9. Web-интерфейс

Web-интерфейс должен быть доступен по адресу:

```http
GET /
```

Web-интерфейс должен обеспечивать:

- регистрацию;
- вход;
- отображение текущего пользователя;
- сохранение JWT между обновлениями страницы;
- выход из учётной записи;
- создание участника;
- просмотр участников;
- создание заявки;
- регистрацию оплаты;
- получение сводного отчёта;
- отображение ошибок API.

### 6.10. Проверка работоспособности

Маршрут:

```http
GET /health
```

должен возвращать:

```json
{
  "status": "ok"
}
```

с HTTP-кодом `200 OK`.

## 7. Сущности и связи

Система содержит сущности:

- User;
- Participant;
- Application;
- Invitation;
- Payment;
- Thesis;
- HotelRequest.

`User` представляет учётную запись и не связан внешним ключом
с `Participant`.

Participant является центральной сущностью предметной области.

Application, Invitation, Payment, Thesis и HotelRequest связаны
с Participant через обязательное поле `participant_id`.

Один Participant может иметь ноль или несколько дочерних записей.

## 8. Бизнес-правила

### 8.1. Подтверждение заявки

Application нельзя перевести в статус `confirmed`, если у связанного
Participant отсутствует Payment со статусом `paid`.

При нарушении правила сервер возвращает:

```text
409 Conflict
```

```json
{
  "detail": "Registration fee must be paid before confirmation"
}
```

### 8.2. Уникальность участника

Поле `Participant.email` должно быть уникальным.

Повторный email должен приводить к ответу `409 Conflict`.

### 8.3. Уникальность пользователя

Поле `User.username` должно быть уникальным.

Повторный username должен приводить к ответу `409 Conflict`.

### 8.4. Хранение пароля

Пароль не должен храниться в открытом виде.

В базе хранится только Argon2-хеш в поле `password_hash`.

Пароль и его хеш не должны возвращаться через API.

### 8.5. JWT

JWT должен содержать:

- `sub` — username пользователя;
- `exp` — время окончания действия токена.

Срок действия задаётся переменной
`ACCESS_TOKEN_EXPIRE_MINUTES`.

## 9. Требования к входным данным

Username должен:

- содержать от 3 до 50 символов;
- состоять из латинских букв, цифр, точки, дефиса
  или подчёркивания.

Password должен содержать от 8 до 128 символов.

Для Participant обязательны:

- `full_name`;
- `email`.

Сумма Payment должна быть больше нуля.

Некорректные данные должны приводить к ответу
`422 Unprocessable Entity`.

## 10. Обработка ошибок

| Код | Назначение |
|---|---|
| `200 OK` | Запрос выполнен |
| `201 Created` | Объект создан |
| `204 No Content` | Объект удалён |
| `401 Unauthorized` | Аутентификация отсутствует или неуспешна |
| `403 Forbidden` | Учётная запись неактивна |
| `404 Not Found` | Объект не найден |
| `409 Conflict` | Нарушено бизнес-правило или уникальность |
| `422 Unprocessable Entity` | Ошибка проверки данных |
| `500 Internal Server Error` | Непредвиденная ошибка |

Ответ об ошибке должен содержать поле `detail`.

## 11. Требования к хранению данных

Данные должны храниться в PostgreSQL.

Для работы с данными используются:

- SQLAlchemy;
- Alembic;
- PostgreSQL;
- psycopg2.

Структура базы изменяется через миграции Alembic.

Пароли хранятся только как Argon2-хеши.

JWT не хранится в таблицах базы данных.

Файлы `.env`, `.venv`, `__pycache__`, локальные базы,
логи и файлы IDE не должны попадать в Git.

## 12. Требования к конфигурации

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к PostgreSQL |
| `JWT_SECRET_KEY` | Секрет подписи JWT |
| `JWT_ALGORITHM` | Алгоритм подписи JWT |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Срок действия JWT |

В репозитории должен находиться `.env.example` без настоящих секретов.

Локальный `.env` должен игнорироваться Git.

## 13. Требования к безопасности

Система должна:

- использовать Argon2;
- не хранить открытые пароли;
- не возвращать пароли и хеши через API;
- использовать подписанные JWT;
- проверять срок действия JWT;
- возвращать одинаковую ошибку для неизвестного пользователя
  и неправильного пароля;
- не добавлять JWT и секреты в Git;
- не показывать JWT пользователю.

В учебном Web-интерфейсе JWT хранится в `localStorage`.
