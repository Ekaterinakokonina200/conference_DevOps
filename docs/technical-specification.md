\# Техническое задание



\## 1. Общие сведения



\### 1.1. Наименование системы



Conference Management System — система управления научной конференцией.



\### 1.2. Назначение документа



Документ определяет функциональные и технические требования

к системе управления научной конференцией.



Структура технического задания подготовлена с учётом основных

разделов ГОСТ 34.602.



\### 1.3. Основание для разработки



Основанием для разработки является лабораторная работа №1

«Сквозной проект и Git-процесс».



\## 2. Назначение системы



Система предназначена для автоматизации основных процессов,

связанных с организацией научной конференции.



Система обеспечивает:



\- регистрацию участников;

\- создание заявок;

\- создание приглашений;

\- регистрацию организационных взносов;

\- учёт тезисов;

\- учёт потребности в гостинице;

\- формирование сводной отчётности.



\## 3. Цели разработки



Основными целями разработки являются:



\- централизованное хранение данных;

\- сокращение ручной обработки информации;

\- контроль статусов заявок;

\- контроль оплаты организационных взносов;

\- автоматизация формирования сводного отчёта;

\- предоставление HTTP API и Web-интерфейса.



\## 4. Категории пользователей



Основными пользователями системы являются:



\- организатор конференции;

\- секретарь конференции;

\- оператор, работающий с данными участников.



Аутентификация и разделение прав доступа не входят

в текущую версию системы.



\## 5. Основные сценарии использования



Пользователь может:



1\. Зарегистрировать нового участника.

2\. Просмотреть список участников.

3\. Изменить данные участника.

4\. Удалить участника.

5\. Создать заявку на участие.

6\. Изменить статус заявки.

7\. Создать приглашение.

8\. Изменить статус приглашения.

9\. Зарегистрировать организационный взнос.

10\. Изменить статус оплаты.

11\. Добавить тезис.

12\. Изменить статус тезиса.

13\. Создать запрос на гостиницу.

14\. Получить сводный отчёт.

15\. Проверить работоспособность приложения.



\## 6. Функциональные требования



\### 6.1. Управление участниками



Система должна обеспечивать:



\- создание Participant;

\- получение списка Participant;

\- получение Participant по идентификатору;

\- изменение Participant;

\- удаление Participant;

\- проверку уникальности email.



\### 6.2. Управление заявками



Система должна обеспечивать:



\- создание Application;

\- получение списка Application;

\- получение Application по идентификатору;

\- изменение статуса Application;

\- удаление Application.



\### 6.3. Управление приглашениями



Система должна обеспечивать:



\- создание Invitation;

\- получение списка Invitation;

\- получение Invitation по идентификатору;

\- изменение статуса Invitation;

\- удаление Invitation.



\### 6.4. Управление оплатами



Система должна обеспечивать:



\- создание Payment;

\- получение списка Payment;

\- получение Payment по идентификатору;

\- изменение статуса Payment;

\- удаление Payment.



\### 6.5. Управление тезисами



Система должна обеспечивать:



\- создание Thesis;

\- получение списка Thesis;

\- получение Thesis по идентификатору;

\- изменение статуса Thesis;

\- удаление Thesis.



\### 6.6. Управление гостиницей



Система должна обеспечивать:



\- создание HotelRequest;

\- получение списка HotelRequest;

\- получение HotelRequest по идентификатору;

\- изменение HotelRequest;

\- удаление HotelRequest.



\### 6.7. Формирование отчёта



Система должна формировать сводный отчёт по адресу:



`GET /reports/summary`



Отчёт должен содержать:



\- количество участников;

\- количество подтверждённых заявок;

\- количество оплаченных взносов;

\- количество тезисов;

\- количество запросов на гостиницу.



Report не является отдельной таблицей базы данных.

Он формируется динамически на основании существующих данных.



\## 7. Сущности системы



Система содержит следующие основные сущности:



\- Participant;

\- Application;

\- Invitation;

\- Payment;

\- Thesis;

\- HotelRequest.



Participant является основной сущностью.



Остальные сущности связаны с Participant через поле

`participant\_id`.
